# Mersad V1 — Dashboard

## 1. Purpose

The Mersad dashboard provides a user interface for viewing security alerts generated by the backend.

Its responsibilities are to:
- Retrieve alerts from the backend API.
- Display alert summary counts.
- Show alert severity and detection rule information.
- Indicate API connectivity.
- Refresh the alert feed automatically.
- Report API errors while retaining previously loaded alert data.

The dashboard does not collect telemetry or execute detection rules.

## 2. Technology

- React for the user interface.
- TypeScript for static type checking.
- Vite for frontend development and builds.
- CSS for layout, styling, and responsive behavior.

Main files:
- src/App.tsx: dashboard component and data-fetching logic.
- src/App.css: dashboard styling.

## 3. Architecture and Data Flow

The dashboard retrieves alerts through the ASP.NET Core backend API. It does not connect directly to PostgreSQL.

`	ext
Mersad Agent
    |
    v
Backend Telemetry API
    |
    v
Telemetry Persistence
    |
    v
Detection Engine
    |
    v
Alert Service
    |
    v
PostgreSQL
    |
    v
GET /api/alerts
    |
    v
React Dashboard
`

The current API URL is http://localhost:5121/api/alerts. It is hardcoded in App.tsx for local development.

## 4. Alert Data Model

The frontend Alert type contains:
- id: alert identifier.
- deviceId: associated device identifier.
- detectionRuleId: detection rule identifier.
- 	itle: alert title.
- description: explanation of the detected behavior.
- severity: severity value.
- status: alert status.
- createdAt: creation timestamp.
- updatedAt: last update timestamp.
- processEventId: optional process-event reference.
- networkEventId: optional network-event reference.

The interface displays severity, rule ID, status, title, description, device ID, and creation time. The event references and update timestamp are not currently displayed.

## 5. Summary Metrics

The dashboard shows three summary metrics:
- **Total Alerts:** number of alerts currently loaded from the API.
- **High Severity:** number of alerts whose severity is exactly High.
- **New:** number of alerts whose status is exactly New.

These counts are calculated in the frontend from the loaded alert array.

## 6. Automatic Refresh

When the component mounts, it immediately requests GET /api/alerts and then repeats the request every five seconds.

The frontend checks the HTTP response and verifies that the returned JSON value is an array before updating its alert state.

When the component unmounts, the polling interval is cleared and a flag prevents completed requests from updating component state. An in-flight request is not explicitly cancelled.

## 7. API Connection Status

The dashboard tracks three states:
- connecting: the initial request has not yet succeeded or failed.
- connected: a request succeeded and returned an array.
- disconnected: a request failed or returned an unsuccessful HTTP response.

The status indicator reflects the most recent request result. It does not independently verify database health or the health of every backend subsystem.

## 8. Error Handling

The dashboard handles unsuccessful HTTP responses, fetch failures, and responses that are not arrays.

If a refresh fails, the dashboard displays an error and retains any alerts loaded successfully earlier. If the first request fails, no previous alert data is available in the component state.

A later successful request clears the error and replaces the displayed alert list.

The frontend does not validate every individual alert field at runtime.

## 9. Alert Presentation

Each alert card displays:
- Severity.
- Detection rule ID.
- Status.
- Title and description.
- Device ID.
- Creation timestamp.

The creation timestamp is formatted using the browser's 	oLocaleString() method, so its presentation depends on the browser's locale and time zone.

High and Medium severity values have specific styling. Other values use the default severity styling.

The layout adapts to narrow screens by stacking the summary cards and arranging alert details vertically.

## 10. Current Limitations

The dashboard does not currently provide:
- Search or filtering.
- Sorting controls or pagination.
- Alert investigation or detail pages.
- Alert acknowledgement or status changes.
- Alert assignment or comments.
- Historical trend charts.
- Device inventory views.
- Authentication or role-based access control.
- A configurable API URL.
- WebSocket or server-sent event updates.

The alert list uses five-second polling.

## 11. Security and Deployment Considerations

The hardcoded localhost API URL is suitable only for the current development setup, not a production deployment.

A deployed dashboard should use a configured API endpoint and an appropriate HTTPS setup.

The backend must enforce authentication and authorization before the application is exposed to untrusted clients. CORS is not a substitute for authentication or authorization.

The dashboard should currently be treated as a development-stage interface rather than a production-ready security operations console.

## 12. Future Direction

Potential improvements include:
- Configurable API base URL.
- Alert search, filtering, and sorting.
- Alert details linked to supporting telemetry.
- Alert acknowledgement and status management.
- Device inventory and device-specific alert views.
- Improved refresh feedback and timestamps.
- Pagination for larger alert volumes.
- Authentication and role-based access control.
- Real-time updates when supported by the backend.

These capabilities should be documented as implemented only after they are verified in the code.

## 13. V1 Summary

The dashboard retrieves persisted alerts from the backend, summarizes alert severity and status, displays key alert information, refreshes automatically, and reports API connectivity failures.

It provides the initial user-facing layer of Mersad's telemetry-to-detection-to-alert pipeline. Investigation workflows, alert management, and production deployment capabilities remain future work.
